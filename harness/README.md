# Magic Panel firmware regression harness

A deterministic, headless simulation of `MagicPanel_v010_5.ino` (ATmega328P @ 16 MHz, two
daisy-chained MAX7221 LED drivers, I2C slave at `0x14`) built on [simavr](https://github.com/buserror/simavr).
It records what the LED panel shows and when, in AVR cycles, so a future build of the firmware
can be proven to display the same patterns at the same times as the build we have today.

- `docs/firmware-map.md` — what the firmware does (pins, protocol, patterns, risks)
- `docs/decisions.md` — every non-obvious choice and assumption, with rationale
- `tests/baselines/<scenario>/` — the golden truth, committed and reviewed like code

## Layout

```
MagicPanel.ino              the sketch under development (edit this one)
MagicPanel_v010_5.ino       the frozen reference specimen (hash-guarded, never modified)
MagicPanel_v010_5.ino.elf   the precompiled reference ELF (flash image == `make reference`)
tools/                      setup.sh, versions.env, build_firmware.py, run_scenario.py,
                            compare.py, compare_all.py, baseline.py, gen_scenarios.py, mplib.py
harness/                    mpsim (C, links libsimavr): parts/max7221, panel, i2c_master, vcd
scenarios/*.yaml            stimulus scripts (generated by tools/gen_scenarios.py, committed)
tests/                      pytest suite (conftest.py), baselines/, mutants/
mcp/                        MCP server for Claude Code (+ .mcp.json at the repo root)
third_party/simavr          pinned submodule (v1.8-8-gfe665ce)
third_party/LedControl      pinned submodule (1.0.6), the only Arduino library used
runs/<id>/                  per-run artefacts (gitignored)
```

## Prerequisites

Everything version-sensitive is pinned in `tools/versions.env` and installed **inside the repo**
by `make setup` (arduino-cli 1.5.1, AVR core 1.8.6 with avr-gcc 7.3.0, PyYAML, mcp, Pillow, pytest). The host
only needs:

| | macOS (Apple Silicon) | Linux x86-64 (Ubuntu 24.04 / CI) |
|---|---|---|
| C compiler | Xcode CLT (`xcode-select --install`) | `build-essential` |
| libelf | `brew install libelf` | `apt-get install libelf-dev pkg-config` |
| Python | 3.11+ (`brew install python`) | 3.11+ (`apt-get install python3-venv`) |
| git, make, curl | present | present |

Network is needed once, for `make setup` (downloads arduino-cli, the AVR core, pip packages).
Nothing else needs it; CI caches those and runs the tests offline.

```sh
git clone --recursive <repo> && cd magicpanel
make setup        # ~2 min the first time
make firmware     # MagicPanel.ino -> build/firmware.elf (+ determinism check)
make reference    # specimen -> build/reference/ (must reproduce the shipped ELF's flash image)
make harness      # harness/mpsim
make test         # everything: regression, determinism, mutation self-test, MCP (pytest)
```

Narrow a run with pytest's own selection, e.g. `.venv/bin/python -m pytest tests/test_regression.py -k cross`,
or `MP_SCENARIOS=cmd_20_cross,mode_2_flashall make test-fast`.

## Running one scenario

```sh
make run SCENARIO=cmd_20_cross          # -> runs/cmd_20_cross/
make compare SCENARIO=cmd_20_cross      # -> PASS/FAIL + runs/cmd_20_cross/diff_report.md
less runs/cmd_20_cross/filmstrip.txt    # what a human looks at
```

Run directory contents:

| File | Contents |
|---|---|
| `display.jsonl` | **primary artefact**: one record per change of the rendered panel: `seq, cycle, ns, grid (8 rows of 8 bits, row 0 top, leftmost column first), rows_hex, intensity[2], shutdown[2] (true = device is shut down), scan_limit[2], display_test[2], decode[2], orphan_bits` |
| `filmstrip.txt` | ASCII render of every display change with cycle/ms timestamps |
| `frames.jsonl` | every 16-bit word latched into either MAX7221 (no-ops included): `cycle, ns, latch, device, reg, reg_name, value, raw` |
| `i2c.jsonl` | every I2C transaction: `cycle, end_cycle, dir, addr, bytes, ack, acked_bytes, nack_timeout, filtered, short_read, stalled, twsr[]` |
| `gpio.jsonl` | changes on watched pins outside the MAX7221/I2C buses, and DDR writes |
| `events.jsonl` | reset, scenario markers, queued stimuli, diagnostics (`malformed_burst`, `undefined_register`, `cpu_stopped`) |
| `trace.vcd` | all watched pins + TWSR + latch/display-change strobes, 1 ps timescale (gtkwave / PulseView) |
| `summary.json` | counts, total cycles, canonical + timing hashes, markers, diagnostics, firmware and toolchain metadata, scenario |
| `stimulus.script` | the line-oriented script mpsim actually executed |

`mpsim` itself:

```
harness/mpsim --elf FW.elf --out DIR [--script FILE | --run-ms N | --run-cycles N]
              [--eeprom FILE] [--eeprom-out FILE] [--no-vcd] [--interactive] [--quiet]
```

`--eeprom-out FILE` writes the final 1024-byte EEPROM image when the run ends.

Script lines: `run_ms N`, `at_ms T i2c_write 0x14 20`, `at_ms T i2c_read 0x14 2`,
`at_ms T i2c_write_read 0x14 16 144` (write the bytes after the length, then read that many with
nothing in between; decision D-22),
`at_ms T gpio_set C2 0`, `at_ms T gpio_release C2`, `at_ms T marker text` (`at_cycle` /
`run_cycles` also accepted). Interactive mode takes the same actions plus `step_ms N`,
`step_cycles N`, `display`, `status`, `quit` on stdin and answers one JSON line each on stdout.

## Watching a sequence as an animated GIF

```sh
make gif SCENARIO=cmd_29_twoloop                      # tests/baselines/cmd_29_twoloop/sequence.gif
make gif SCENARIO=cmd_29_twoloop RUN=1                # runs/cmd_29_twoloop/sequence.gif
make gif SCENARIO=cmd_21_cyloncol GIF_ARGS="--speed 0.25"   # 4x slow motion
make gifs                                             # every baseline
```

`tools/render_gif.py` draws each panel state as an 8×8 LED grid (brightness follows the
intensity register, shut-down devices go dark) with the state index, simulated time, the
active command marker and a progress bar. Frame durations are the real gaps between states
(cycles ÷ 16 000 ms), so the GIF plays at the panel's actual speed. GIF viewers cannot show
gaps under ~20 ms, so the ~0.5 ms intermediate latch states of a `PrintGrid()` are merged
into the next visible frame without moving the timeline; `--all-states` shows every one with
a fixed hold instead (timing is then not real), and `--min-frame-ms` tunes the merge. GIFs
are derived artefacts and are not committed. The MCP tool `render_gif` does the same.

## Reading a diff report

`diff_report.md` is written next to every compared run. Comparison runs in **settled** mode by
default (`MP_COMPARE_MODE`, default settle threshold 10 ms via `MP_SETTLE_MS`, per-scenario
`compare_mode`/`settle_ms`): only states that stayed visible for at least the threshold are
compared, so the intermediate latches while a `PrintGrid()` is clocked out do not count. `latch`
mode compares every latch. The report states, in order:

1. **PASS/FAIL** and the firmware hashes of both sides.
2. **Display sequence**: the first state index where the *content* differs (ignoring timing),
   the pattern that was running (from the scenario's markers, e.g. `during "cmd 20 Cross"`),
   the baseline and actual grids side by side with `<-- differs` on changed rows, and the 3
   states before and after for context. "EXTRA"/"MISSING states" means one side has more.
3. **Timing**: if the content matched, the first state whose cycle differs by more than the
   scenario's tolerance (default 0), and a drift summary (max, final, drift at each marker).
   A timing-only failure with matching content means the pattern is right but its speed changed.
4. **Canonical hash** of both sides (the fast CI signal).

Two things worth knowing when reading grids: a `PrintGrid()` in the firmware is 16 bursts over
~7.5 ms, so a pattern change appears as up to 16 successive states (rows filling in); and
`intensity 15/15` etc. after each grid is the per-device status line.

## Adding a scenario

Create `scenarios/<name>.yaml` (`name` must equal the file stem):

```yaml
name: my_case
description: what this exercises and why
firmware_reset: true
eeprom: default              # or a path to a 1024-byte image
run_ms: 6000                 # cycle budget = run_ms * 16000
# timing_tolerance_cycles: 0 # per-scenario override; requires timing_tolerance_reason
steps:
  - at_ms: 100
    i2c_write: { addr: 0x14, bytes: [20] }   # one byte per command for today's firmware
  - at_ms: 3500
    i2c_read: { addr: 0x14, n: 2 }
  - at_ms: 3600
    i2c_write_read: { addr: 0x14, bytes: [0x90], n: 16 }   # register pointer, then read
  - at_ms: 4000
    gpio_set: { pin: C2, value: 0 }          # active-low rotary/jumper inputs
  - at_ms: 5000
    gpio_release: { pin: C2 }
  - at_ms: 5500
    marker: "free-text marker"
```

Then `make run SCENARIO=my_case`, inspect `runs/my_case/filmstrip.txt`, and when it shows what
you intend, `make baseline` captures it (only scenarios without a baseline are written). Commit
`scenarios/my_case.yaml` and `tests/baselines/my_case/` together. The 73 generated scenarios
come from `tools/gen_scenarios.py`; edit that and regenerate rather than hand-editing them.

## How and when to re-baseline

A baseline changes only when the firmware's *intended* behaviour changes. Baselines were captured
from the frozen specimen; re-baselining captures from the dev sketch's `build/firmware.elf`.
Never re-baseline to make a red build green. Procedure:

1. Look at `runs/<scenario>/diff_report.md` and decide whether the change is intended.
2. `make rebaseline SCENARIO=<name> I_MEAN_IT=1` — refuses without `I_MEAN_IT=1`. It re-runs the
   scenario, overwrites `tests/baselines/<name>/`, and writes `rebaseline_diff.md` there showing
   exactly what changed relative to the previous baseline.
3. Commit the baseline and its `rebaseline_diff.md`; the reviewer reads the diff like code.

From Claude Code, `update_baseline(scenario)` returns the diff it would enshrine and applies
nothing until called again with `confirm=true`. Toolchain or harness changes (anything in
`tools/versions.env`, the submodules, or `harness/`) should be followed by `make test`; if the
baselines move, that is a finding to understand, not something to paper over.

## MCP server (Claude Code)

`.mcp.json` registers `magicpanel` (stdio, `mcp/serve.sh` → `.venv/bin/python mcp/magicpanel_server.py`).
Tools: `build_firmware`, `list_scenarios`, `describe_firmware`, `run_scenario`,
`compare_to_baseline`, `run_all`, `sim_start`, `sim_step`, `sim_i2c_write`, `sim_i2c_read`, `sim_i2c_write_read`,
`sim_set_gpio`, `sim_release_gpio`, `sim_get_display`, `sim_get_log`, `sim_stop`,
`update_baseline` (gated). Typical interactive use: `sim_start` → `sim_step ms=100` →
`sim_i2c_write bytes=[20]` → `sim_step ms=200` → `sim_get_display`. Session logs live under
`runs/sessions/<id>/`.

## Known limitations of the simulation

What simavr models well here: the AVR core cycle-accurately (so `delay()`, `millis()`, the
bit-banged MAX7221 timing and ISR nesting are faithful), Timer0, the TWI state machine as seen
by the firmware (status codes, ACK/NACK), GPIO with internal pull-ups, EEPROM.

What it does not model, and how the harness copes:

- **I2C is transaction-level, not wire-level.** No SDA/SCL edges, bus capacitance, clock
  stretching, arbitration or glitches; a byte takes 9 "bit times" derived from the slave's
  TWBR (100 kHz). The harness applies the address filter itself and does not send STOP after
  reads (decisions D-9 to D-11) to avoid simavr artefacts real hardware does not have.
- **ADC**: returns the value injected, default 0. The firmware's `randomSeed(analogRead(A3))`
  therefore does nothing and every run uses avr-libc's default seed. Random patterns are
  deterministic in simulation but will not match any single hardware run (D-1/D-16).
- **Bootloader, fuses, brown-out, power sequencing** are not simulated; cycle 0 is the sketch's
  reset vector, ~1 s after real power-on.
- **MAX7221 electrical behaviour** (LED current, intensity PWM, multiplex scan) is not
  modelled; intensity/scan-limit/shutdown/display-test are tracked as register state and
  applied to the rendered grid logically. Bits written to the nibble that has no LED wired are
  not rendered but are counted as `orphan_bits` so they still change the canonical sequence.
- **Panel orientation**: the rendered grid is the panel as installed in a dome, where v010.5's
  patterns look as named (A-1, D-25); on the bench it appears rotated 180°.
- **Long delays**: `allONTimed(0)` blocks for 1000 s of simulated time; scenarios observe the
  ON state and stop rather than waiting it out.
- **Speed**: ~130 M cycles/s on an M-series Mac; the full suite (443 s simulated) takes about a
  minute, the determinism test twice that.
